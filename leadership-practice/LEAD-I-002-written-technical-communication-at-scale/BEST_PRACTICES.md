# LEAD-I-002 — Written technical communication at scale

## Best practices
- Start with the reader's decision, operating task, or migration need rather than the author's chronology.
- Give RFCs a concise summary, explicit non-goals, alternatives, decision owner, and review deadline.
- Link accepted decisions to implementation, service catalogs, and runbooks so documentation remains discoverable at the point of work.
- Separate durable decision records from live facilitation notes; this kit scales asynchronous understanding rather than owning a review meeting.
- Define intended audiences and distribution channels before publishing, including how remote and cross-time-zone readers can respond.
- Measure useful uptake through qualified readers, references, adoption, and resolved questions instead of document count.
- Assign an owner and review date so stale guidance is corrected, superseded, or archived visibly.

## Four habits
1. Publish a written proposal with a clear ask before scheduling synchronous discussion.
2. Add summaries, headings, status, owners, and stable links to every durable technical document.
3. Link accepted decisions from code, runbooks, and onboarding paths where readers need them.
4. Review uptake and freshness on a regular cadence, then close discoverability gaps.
